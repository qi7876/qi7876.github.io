## 工作模型

项目管理的核心不是管理任务，而是持续获得结果、减少不确定性，并根据反馈调整方向

整个项目可以从粗到细分为：

1. Goal
    - 项目当前希望达到的最终结果
    - Goal 包括要解决的问题、为什么值得解决、成功标准、关键约束
1. Milestone
    - 一个可以独立验收的阶段性结果，用来推动项目向 Goal 前进
    - Milestone 应该有明确目标和验收条件、解决一个重要阶段问题、降低一部分关键风险、为下一阶段提供决策依据
1. Task：
    - 短期、可执行的工作单元，验收标准为需要得到什么结果或证据
    - Task 产生：
        - Result：实际结果
        - Learning：获得的新信息
        - Decision：由结果支持的决策

## 工作原则

1. 管理结果
    - 明确要解决的问题和验收条件
    - 区分：
        - Outcome：希望产生的实际效果
        - Output：实现、文档、实验等产物
        - Learning：通过工作获得的知识和证据
    - 负面结果同样是有效结果，只要它减少了不确定性并支持后续决策
1. 结果驱动反馈：
    - 滚动规划：从Goal得到当前的Milestone，再得到当前的Tasks，根据结果形成下一个Milestone
    - 快速反馈循环：Task → Result → Learning → Decision → Next，通常在当前 Milestone 内调整下一步，如果发现影响关键假设或项目方向的新证据，则升级到方向调整
    - 方向反馈循环：Milestone → Review → Reassess Goal / Direction → Next Milestone
1. 优先验证风险：优先处理最可能导致项目失败、返工或方向错误的未知问题
1. 任务可执行：拆分复杂工作，普通任务尽量在几小时到一两天内完成
1. 限制 WIP：
    - 每人一个主要任务
    - 只有当前任务被阻塞时才可推进一个副任务
    - 应该优先解决阻塞其他人进展的任务
1. 及时同步：重要信息及时同步和记录，比如新结果、新风险、阻塞、假设变化、范围变化、重要决策

## GitHub

1. Task：
    - 以Issue的形式存在，写清楚目标和验收条件，可结合 PR 解决
    - 通过 Issue 评论及时记录新的依赖、风险、阻塞、证据、结果、结论和决策
    - 验收完成后关闭 Issue
1. Milestone：
    - 使用 Milestone 管理，写清楚目标和验收条件
    - 关联 Issue (Task)
    - 验收完成后关闭 Milestone
1. Goal：将目标和验收条件记录在 README 中
